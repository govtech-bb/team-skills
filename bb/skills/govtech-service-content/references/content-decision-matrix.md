# Content decision matrix

Use this reference when the requested output or journey is unclear. It is a decision aid, not a page menu for the user.

## First decision

Identify the user’s primary need and choose the smallest content journey that meets it.

| Primary user need | Default model | Key test | Do not use it when |
|---|---|---|---|
| Understand a service before choosing whether to use it | Entry page | Users need orientation before commitment | There is only one simple route and the start information can fit on one page |
| Prepare and begin one transaction | Start page | Users know the service and need requirements before starting | Users first need to compare routes or understand whether the service applies |
| Understand and begin one simple transaction | Combined service and start page | One audience, one route and little preparation content | The page becomes long, several routes exist or guidance must stand alone |
| Choose between destinations or service routes | Routing page | The choice changes where users go | One route merely has conditional form questions |
| Understand a rule, process or non-transactional subject | Guidance page | The next need is understanding or preparation | The main action is to start a transaction |
| Prepare documents or information before a later action | What-you-need page | The preparation list is substantial and reusable | The list is short enough for the start page |
| Complete a digital application, report, registration or request | Form | The service must collect information or agreement | Content only needs to explain or route |
| Know that submission succeeded and what follows | Confirmation screen, with email when supported | The system has accepted the submission | The outcome is still pending before submission completes |
| Decide whether to contact a public office | Public office page | The office itself is a useful public destination | Users need a transaction, general programme guidance or staff routing |
| Identify the current holder of a significant public role | Role-holder page | There is a demonstrated public identification need and a maintenance owner | The request is a biography or prestige profile |
| Route, authorise or escalate government work | Internal MDA page | Staff need operational rules | The audience is the public |
| Understand or take part in a public programme | MDA public guidance | The need is evergreen explanation, preparation or participation | The content is news, a campaign or a transaction by itself |
| Compare and prioritise several existing services | Content audit | A portfolio decision is required | The user needs one page drafted |

## Combine or separate

Combine components only when all are true:

- they serve the same primary audience and need
- they appear at the same point in the journey
- one clear next action remains
- combining does not hide eligibility, preparation or routing
- the result stays scannable on mobile

Separate when any are true:

- audiences differ
- users must make a consequential choice before proceeding
- guidance must be found or maintained independently
- preparation is substantial
- public and internal information would mix
- role-holder information would duplicate office responsibilities
- one component changes more often than the other

## Common request corrections

| User asks for | Diagnose before accepting | Likely correction |
|---|---|---|
| “An information page and start page” | Is there one simple route and short preparation? | Combine when separation would repeat content |
| “Put everything on one page” | Are there several needs, audiences or journey stages? | Separate by need or stage |
| “A page for our department” | What should the public decide or do? | Use office contact content, public guidance or service content based on the need |
| “A profile for the head” | Does the public need to identify the holder? | Create a role-holder page only if the need test passes |
| “Digitise this paper form” | Is the paper form current and what journey surrounds it? | Preserve meaning, redesign for digital use and add supporting journey content where evidenced |
| “Add a contact directory” | What purpose does each route serve? | Organise by user need or omit unrelated routes |
| “Create awareness content” | What must the audience understand or do? | Define a service or guidance need, or state that campaign content is outside scope |

## Evidence boundary

This matrix decides structure. It does not supply service facts.

Never infer eligibility, fees, deadlines, legal rules, locations, contacts, authority, processing times or outcomes from the selected model.

When evidence is missing, follow the evidence and escalation reference and produce only the safest supported output.
